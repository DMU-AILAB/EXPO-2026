# 배경 네거티브 학습 효과 평가 리포트 (v4 → v5 → v6)

**평가 일시:** 2026-08-26
**평가 환경:** NVIDIA GeForce RTX 3060, Ultralytics 8.4.90, PyTorch 2.12.1+cu130 (`expo` conda env)
**평가 대상:** `white_cane_v4_320`(기존) / `white_cane_v5_320`(신규 학습) / `white_cane_v5b_ft320`(파인튜닝)

---

## 1. 배경 — 왜 했나

`datasets/sources/background_photos/`(이전 `extra_data/`)에는 흰 지팡이도 사람도 없는 일반 배경 사진이 모여 있다. 이 사진들에 기존
`white_cane_v4_320`를 돌려보니(imgsz=320, conf=0.25) **272장 중 78장(28.7%)에서 오탐지**가 났다.

- `white_cane` 오탐지: 32장 / 37박스 (최고 conf 0.77)
- `person` 오탐지: 55장 / 80박스 (최고 conf 0.83)

즉 이 폴더는 현행 모델이 실제로 틀리는 **하드 네거티브 모음**이다. YOLO는 라벨 파일이 빈
이미지를 배경(negative)으로 학습하므로, 이를 train에 넣어 오탐지(KPI: FPR ≤ 5%)를 줄이는 것이
이번 작업의 목표다.

## 2. 데이터 준비 (`prepare_background_dataset.py`)

| 단계 | 내용 |
|---|---|
| 수동 검수 | 289장 → 272장 (작업자가 사람 찍힌 사진 17장 제거) |
| 자동 스크리닝 | COCO yolov8n으로 272장 전수 스캔 → 22장에서 person 감지. 육안 확인 결과 대부분 COCO 오탐지(마네킹·볼라드·의자·장난감·유모차)였으나 **실제 사람이 있는 4장이 검수에서 누락**됨 |
| 최종 제외 | `263.jpg`(보행자 5~6명), `39.jpeg`, `270.jpg`, `228.HEIC`(인물 등신대) → **268장** |
| 정규화 | HEIC/avif/webp 혼재 + 폰 EXIF 회전 → `exif_transpose` → RGB → 최대변 640 jpg(q92). 1.08GB → 21.9MB |
| 리네임 | `bg_%04d.jpg` — 원본에 `1.jpg`/`1.JPG`처럼 확장자만 다른 같은 stem이 있어 YOLO의 stem 기반 이미지↔라벨 매칭이 충돌한다 |
| 분할 | train 228장 / FP 벤치 홀드아웃 40장. 홀드아웃은 v4 오탐지 여부(`cane_fp`/`person_fp`/`clean`)로 **층화 추출** — 단순 무작위로는 오탐지 이미지가 거의 안 들어가 지표가 둔감해진다 |

학습셋 최종: train 11,116장 중 **231 backgrounds**(신규 228 + 기존 3), 0 corrupt.
val/test는 건드리지 않아 v4 지표와 직접 비교 가능하다.

**사람이 찍힌 배경을 반드시 빼야 하는 이유**: 라벨 없이 배경으로 넣으면 YOLO가 그 사람 영역을
"배경(사람 아님)"으로 학습해 person 재현율이 떨어진다. `merge_person_dataset.py` 병합 때 발생한
라벨 누락 문제와 정확히 같은 종류의 오염이다.

### 4-3. 채택 판정

사전에 정한 기준을 순서대로 적용한다.

1. **cane recall이 v4 대비 1%p 이상 하락하지 않을 것** — 안전 기능이라 재현율 손실이 오탐지보다
   치명적이다. v5 −0.1%p, v5b **+0.1%p** → 둘 다 통과
2. **배경 홀드아웃 FP 박스 수 최소** — v5b 3박스 < v5 4박스 → **v5b 채택**

v5b는 부차 지표(test mAP50 0.974, mAP50-95 0.793, cane mAP50 0.990)에서도 모두 최고이거나
v4와 동등하다. 파인튜닝의 우려였던 배경 과적합에 의한 재현율 저하는 나타나지 않았다.

**요약: 배경 오탐지 박스 14 → 3 (−79%), 지팡이 재현율은 0.978 → 0.979로 유지.**

## 5. INT8 양자화 (Pi 배포용)

`docs/int8_320_quantization_report.md`에서 검증된 calibration 설정(`split=train fraction=0.1`,
변형 A1)을 그대로 적용했다. calibration에 val split을 쓰면 recall이 급락하는 아티팩트가 있다.

```bash
yolo export model=runs/white_cane_v5b_ft320/weights/best.pt \
  format=tflite int8=True imgsz=320 data=datasets/data.yaml split=train fraction=0.1
```

test split(1,099장, imgsz=320) 기준 두 경로를 모두 측정했다.

| 형식 | 파일 | I/O | cane R | mAP50 | mAP 손실 | 배경 FP (conf 0.25) |
|---|---|---|---|---|---|---|
| FP32 (PT) | `weights/best.pt` | float32 | 0.979 | 0.990 | — | 3박스 |
| **INT8 LiteRT (A1) ⭐** | `weights/best_int8.tflite` (3.3MB) | float32 NCHW | **0.960** | **0.971** | **-1.9%** | **3박스** |
| full-integer (onnx2tf) | `weights/best_saved_model/best_full_integer_quant.tflite` (3.2MB) | int8 NHWC | 0.924 | 0.950 | -4.0% | 3박스 |

- 두 경로 모두 mAP 손실이 KPI(≤5%)를 만족하지만, **이번 모델에서는 LiteRT A1 경로가 더 정확했다**
  (cane recall 0.960 vs 0.924). `docs/int8_320_quantization_report.md`의 v3 측정에서는 반대로
  full-integer가 우세했으므로, 모델이 바뀌면 두 경로를 다시 비교해야 한다 — 어느 한쪽이 항상
  낫다고 가정하지 말 것.
- **양자화 후에도 배경 오탐지가 되돌아오지 않았다**(세 형식 모두 3박스) — 이번 작업의 효과가
  int8 배포 경로까지 살아남는다는 뜻이다.
- 출력 형상은 세 형식 모두 `[1,6,2100]`으로 v4와 동일 — `yolo_postprocess.py` 수정 불필요.
- 입력 레이아웃은 LiteRT가 NCHW `[1,3,320,320]` float32, full-integer가 NHWC `[1,320,320,3]` int8이다.
  `yolo_postprocess.set_input`이 `is_nchw`를 자동감지하므로 양쪽 모두 추가 수정 없이 동작한다.

### EdgeTPU 컴파일 (미완 — 후속 작업)

`format=edgetpu` export는 `best_full_integer_quant.tflite`까지 정상 생성했으나, 마지막
`edgetpu_compiler` 호출 단계에서 실패했다. 이 머신에 컴파일러가 없고 ultralytics가 자동으로
`sudo apt`로 설치하려다 비대화형 셸에서 권한을 얻지 못했기 때문이다
(`CalledProcessError: 'sudo mkdir -p /etc/apt/keyrings'`).

```bash
# 컴파일러 설치 후 수동 컴파일 (Coral 공식 저장소)
echo "deb https://packages.cloud.google.com/apt coral-edgetpu-stable main"   | sudo tee /etc/apt/sources.list.d/coral-edgetpu.list
curl -fsSL https://packages.cloud.google.com/apt/doc/apt-key.gpg | sudo apt-key add -
sudo apt update && sudo apt install -y edgetpu-compiler

edgetpu_compiler -s runs/white_cane_v5b_ft320/weights/best_saved_model/best_full_integer_quant.tflite
```

산출된 `*_edgetpu.tflite`는 `camera_live_pi.py`가 찾는 경로 규칙(`_model_paths()`)에 맞춰
`runs/white_cane_v5b_ft320/weights/best_int8_edgetpu.tflite`로 배치해야 Coral 백엔드가 잡는다.
컴파일 전까지 `v5b_320` 프로필은 CPU TFLite 경로(`best_int8.tflite`)로 동작한다.

## 7. 한계 / 후속 작업

- **도메인 불일치**: 배경 원본은 오페라하우스·거실·해변 같은 일반 사진이라 실제 배치 환경
  (지하철 역사, 횡단보도)과 다르다. 일반적 오탐지 억제엔 효과가 확인됐지만, 현장 특유의
  오탐지원(손잡이·점자블록·기둥·우산·청소도구)에는 제한적이다. **가장 가치 높은 네거티브는
  실제 설치 현장을 찍은 배경 사진**이므로, 데모 전 현장 촬영본을 같은 파이프라인
  (`prepare_background_dataset.py`)으로 추가 편입할 것을 권장한다.
  (현장 오탐지의 즉시 대응 수단으로는 `zone_type="exclude"` 감지 제외구역이 이미 있다.)
- **person 재현율 감시**: 배경 268장 중 COCO가 사람으로 오인한 22장 대부분은 마네킹·인쇄물 등
  "사람 비슷한 것"이다. 이를 배경으로 학습시키는 건 의도된 효과지만, 향후 배경을 더 추가할 때마다
  test person recall을 함께 확인해야 한다(현재 0.920, v4 0.923).
- **유사물 구분은 이 작업의 범위 밖이었다** — 후속 작업으로 진행 중.
  배경 원본은 일반 배경이라 "없는 것을 있다고 하지 않는" 능력만 가르쳤고, 등산스틱·우산·
  난간처럼 **지팡이와 형태가 유사한 물체를 구분하는 능력**은 다루지 못했다. 실제로 v5b가 남긴
  유일한 지팡이 오탐지(`136.JPG`, conf 0.52)도 사람 발치의 가는 금속 기둥이다. 데이터셋에
  유사물이 "지팡이 아님"으로 라벨링된 사례가 하나도 없는 것이 근본 원인이며,
  `prepare_lookalike_dataset.py`와 런타임 방어선(사람 동반 필수 조건, 오탐지 핫스팟 제안)이
  이를 겨냥한다.
- **Pi 실기기 검증 미완**: 온디바이스 FPS와 실제 현장 오탐지 빈도는 `make sync` 후 확인 필요.
- **EdgeTPU 컴파일 미완**: §5 참고. 컴파일 전까지 `v5b_320`은 CPU TFLite로만 동작한다.
- `pi-heif`는 HEIC 원본을 읽기 위한 `prepare_background_dataset.py` 전용 의존성이다.
  1회성 스크립트라 `requirements.txt`에는 넣지 않고 스크립트 docstring에 설치 명령을 적어두었다.

## 8. 유사물 네거티브 (v6) — 2차 작업

### 8-1. 왜 했나

v5b가 배경 오탐지는 14 → 3박스로 줄였지만, 사용자가 실제로 겪는 실패는 **등산스틱·목발·
빗자루처럼 흰 지팡이와 형태가 닮은 물체를 지팡이로 오탐지해 엉뚱한 음성이 재생되는 것**이다.
§7에 적었듯 일반 배경은 "없는 것을 있다고 하지 않는" 능력만 가르치고, 유사물 구분은 못 가르친다.
데이터셋에 유사물이 "지팡이 아님"으로 라벨링된 사례가 **하나도 없는 것**이 근본 원인이다.

측정해보니 실제로 심했다 — v5b는 유사물 홀드아웃 136장 중 **42장에서 지팡이 오탐지 75박스**
(conf 0.25, 최고 conf 0.878)를 냈다. 배경 홀드아웃(40장 중 3박스)과는 자릿수가 다르다.

### 8-2. 데이터 준비

공개 데이터셋을 **색인으로만** 써서 684장을 모았다(`fetch_lvis_lookalikes.py`,
`fetch_openimages_lookalikes.py`). 어노테이션은 "유사물이 찍힌 이미지를 찾는" 용도이고,
**유사물에는 어떤 박스도 그리지 않는다** — 그게 이 데이터의 본체다. person 라벨만 COCO
yolov8n으로 새로 붙인다(LVIS의 person 라벨은 federated 어노테이션이라 신뢰 불가).

| 출처 | 카테고리 | 장수 |
|---|---|---|
| LVIS | `ski_pole` 150 / `baseball_bat` 150 (면적순 상위 N) | 300 |
| LVIS | `broom` 92 / `walking_cane` 84 / `shovel` 74 / `mop` 22 / `walking_stick` 14 / `crutch` 13 (전량) | 299 |
| Open Images V7 | `Crutch` (LVIS에 13장뿐이라 보완) | 85 |
| | **합계** | **684** |

- **umbrella는 뺐다** — LVIS 우산은 대부분 펼친 우산/파라솔이라 캐노피가 지팡이와 안 닮는다
- **고정 수직 구조물(pole 등)도 뺐다** — 움직임 게이트가 코드 수준에서 막으므로 데이터로
  가르치는 것보다 저렴하고 확실하다
- **흰지팡이 혼입은 2중 차단** — `CANE_RISK`가 `walking_cane`/`walking_stick`이 함께 라벨된
  이미지를 다른 카테고리에서 배제하고, 그 두 카테고리는 육안 검수해 3장을 `lookalike_exclude.txt`로
  뺐다. 흰지팡이가 네거티브로 섞이면 "흰지팡이는 지팡이가 아니다"를 가르쳐 정반대 효과가 난다

681장 중 **136장은 홀드아웃**, 544장을 `datasets/train/`에 `lk_XXXX.jpg`로 편입했다
(with_person 458 / solo 86). 네거티브 비율 (228+544)/11,660 = **6.6%** — 권장 범위(0~10%) 안이다.

> 홀드아웃 136장은 `eval_background_fp.py --classes 0`과 함께 쓴다. `with_person` 이미지에는
> 사람이 실제로 찍혀 있어 person 탐지는 오탐지가 아니므로, 지팡이만 세면 전량을 벤치에 쓸 수
> 있다. solo만 쓰면 18장으로 줄어 지표가 둔감해진다.

### 8-4. 채택 판정

1. **cane recall이 v5b(0.979) 대비 1%p 이상 하락하지 않을 것** — v6_ft −0.6%p 통과,
   v6_320 **−1.3%p 탈락**
2. 그중 유사물 홀드아웃 FP 최소 — 남은 후보가 v6_ft 하나 → **v6_ft320 채택**

유사물 FP만 보면 v6_320(2박스)이 v6_ft(6박스)보다 낫지만, 재현율이 기준선이다. 안전 기능이라
"지팡이를 놓치는 것"이 "가끔 헛안내하는 것"보다 치명적이고, 헛안내 쪽은 런타임 3중 게이트가
한 겹 더 막는다.

**요약: 유사물 오탐지 75 → 6박스 (−92%), 배경 지팡이 오탐지 1 → 0박스, 지팡이 재현율
0.979 → 0.973.**

### 8-4-1. INT8 양자화 (Pi 배포용)

§5와 같은 검증된 calibration 설정으로 변환했다.

```bash
yolo export model=runs/white_cane_v6_ft320/weights/best.pt \
  format=tflite int8=True imgsz=320 data=datasets/data.yaml split=train fraction=0.1
```

| | cane R | cane mAP50 | person R | mAP50 | 유사물 FP | 배경 FP(cane/person) |
|---|---|---|---|---|---|---|
| v6_ft320 FP32 | 0.973 | 0.982 | 0.916 | 0.968 | 6박스 | 6 (0 / 6) |
| **v6_ft320 INT8** | 0.958 | 0.971 | 0.915 | 0.957 | **6박스** | **6 (0 / 6)** |
| (참고) v5b INT8 | 0.960 | — | — | — | 미측정 | — |

양자화 손실은 지팡이 재현율 −1.5%p로 v5b(−1.9%p)와 같은 수준이고, **이번 작업의 성과인
유사물/배경 오탐지 억제는 INT8에서도 그대로 유지된다**(6박스 / 0박스). 산출물은
`runs/white_cane_v6_ft320/weights/best_int8.tflite` (3.2MB, 모델 크기 KPI 10MB 이내).

### 8-5. 관찰 — 배경 홀드아웃의 person 오탐지 증가 (2 → 6박스)

배경 홀드아웃에는 사람이 없는데(사람이 찍힌 4장은 `prepare_background_dataset.EXCLUDE`로 제외)
person 오탐지가 늘었다. 유사물 데이터의 458장이 person만 라벨링된 `with_person` 이미지라
person 쪽 결정 경계가 더 관대해진 것으로 보인다.

**트리거 경로에는 영향이 없다** — ROI 트리거 루프는 `cane_tracks`(지팡이 클래스)만 순회하므로
사람 단독 탐지로는 음성이 나가지 않는다. 다만 사람 동반 필수 조건이 사람 탐지에 의존하므로,
person이 과하게 잡히면 그 게이트가 느슨해지는 방향이다(놓치는 쪽이 아니라 통과시키는 쪽).
배경 지팡이 오탐지 자체는 1 → 0으로 줄었고, 유동인구 집계는 트랙 소멸 기준이라 단발 오탐지에
둔감하다. 유사물을 더 늘릴 때는 이 수치를 계속 볼 것.

## 9. PC 실파이프라인 검증 — 연관 로직 결함 발견 및 수정

§8까지는 정지 이미지 벤치였다. `camera_live_pi.py`를 **PC에서 영상 파일 소스로** 돌려
(Pi 배포본과 같은 코드) 실제 트리거 경로를 검증한 결과, 모델과 무관한 런타임 결함이 나왔다.

입력: `docs/presentation/KakaoTalk_20260729_175616347.mp4` (805프레임, 흰지팡이 사용자 +
난간·나무가 같은 프레임에 있는 야외 장면). v5b/v6 두 프로필을 한 프로세스에 띄워 벽시계
조건을 동일하게 맞췄다.

> `docs/presentation/시연영상.mp4`는 쓰지 말 것 — 대시보드 화면을 녹화한 영상이라
> 브라우저 UI 안에 이미 박스가 그려져 있어 입력으로 부적합하다.

### 9-1. 증상 — 트리거 0회

두 모델 모두 **한 번도 트리거되지 않았다.** 게이트 단계별 통과 프레임(conf 0.40):

| 단계 | v5b | v6 |
|---|---|---|
| 지팡이 탐지 프레임 | 59 | 63 |
| 정지 억제 후 | 172 | 208 |
| 움직임 게이트 후 | 41 | 78 |
| **사람 동반 후** | **8** | **20** |

차단된 것을 눈으로 확인한 결과 **전부 진짜 지팡이**였다. 게다가 통과 프레임이 띄엄띄엄해
(v6 최장 연속 11프레임) 디바운스 0.5초를 채우지 못했다.

### 9-2. 원인 — 중심점 포함 판정이 지팡이 자세와 안 맞음

`cane_person_assoc._matched_pairs()`는 사람 bbox를 좌우 15% 확장한 뒤 지팡이 bbox의
**중심점**이 그 안인지를 봤다. 흰 지팡이는 몸 앞으로 비스듬히 뻗어 짚기 때문에 중심점이
자주 밖으로 나간다. 사람 1명 + 지팡이 탐지가 있는 60프레임 실측:

| 기준 | 통과 |
|---|---|
| 옛 기준 (중심점 ∈ 좌우 15% 확장 bbox) | **19 / 60** |
| 두 bbox의 최단거리 = 0 (겹침) | **60 / 60** |
| 지팡이 중심 y ∈ 사람 y 범위 | **60 / 60** |

즉 판정 축(세로)이 아니라 "중심점 하나로 본다"는 방식이 문제였다.

### 9-3. 수정 결과

판정을 **"최단거리 ≤ 사람 폭 × 0.15 AND 지팡이 중심 y가 사람 y 범위 안"**으로 교체했다.
두 박스가 겹치면 거리가 0이라 옛 기준으로 통과하던 것은 전부 계속 통과한다(하위호환).

| | 수정 전 | 수정 후 |
|---|---|---|
| 사람 동반 후 통과 프레임 (v6) | 20 | **78** |
| 최장 연속 통과 구간 (v6) | 11프레임 | **40프레임** |
| 실파이프라인 트리거 (150초 구동) | **0회** | **7회** (v5b/v6 각각) |

### 9-4. 부수 발견 — 트랙 안정성과 유동인구 통계

같은 영상의 트랙 생존:

| | 트랙 수 | 최장 생존 | 최대 변위 |
|---|---|---|---|
| 사람 | 11 | **805프레임(전체)** | 924px |
| 지팡이 | 10 | **58프레임** | 167px |

지팡이 트랙이 죽을 때마다 `max_disp`가 리셋되어 움직임 게이트를 처음부터 다시 증명해야
한다. 이 비대칭이 다음 작업(병합 객체를 **사람 트랙에 고정**)의 근거다.

또한 `FootTrafficCounter`의 지팡이 사용자 판정(`cane_ratio_threshold=0.3`)에 별개의 결함이
드러났다 — **트래킹이 좋아질수록 불리해진다.**

| 모델 | 주 사람 트랙 | 지팡이 동반 | 비율 | 판정 |
|---|---|---|---|---|
| v5b | 522프레임(끊김) | 160 | 30.7% | 지팡이 사용자 ✓ |
| v6 | 805프레임(전체) | 186 | **23.1%** | 미달 ✗ |

트랙이 길수록 분모에 "사람이 멀어 지팡이가 안 잡히는 구간"이 들어가 비율이 희석된다.
탐지 품질이 아니라 트랙 길이가 판정을 가르는 구조이며, 이번 수정과 무관한 선행 결함이다
(트리거 경로는 프레임 단위라 영향 없음). 후속 작업에서 다룬다.
