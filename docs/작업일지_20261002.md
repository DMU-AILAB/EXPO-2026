## 구현 내용

### 1. Pi 소프트웨어 통일
- 코드(`device/*.py`)는 세 장치가 사실상 동일했고, 차이는 **systemd 유닛과 설정**이었음.
- 60번의 `visionguide-device` / `visionguide-roi-editor` 유닛을 기준으로 89 · 103번에 적용.
- `deploy/visionguide-device.service` 템플릿: `--inference-backend auto --auto-hardware`.
- Coral 추론은 원래 `~/.python39` 서브프로세스(`edgetpu_infer.py`)가 처리함 → 메인 프로세스는 시스템 `python3`면 충분.
  89번이 메인을 python3.9로 띄워서 picamera2 · ROI 모듈이 없어 카메라 파이프라인이 재시작을 반복하고 있었음.
- 장치별로 달라야 하는 값은 통일하지 않음: `device_identity.json`, RF `group_priority`(100/101/102), RF 하드웨어 설정.

### 2. 적응형 하드웨어 (`device/camera_config.py`, `device/camera_live_pi.py`)
- `coral_present()` — USB(`1a6e:089a`, `18d1:9302`) 또는 PCIe(`/dev/apex_*`)로 Coral 감지.
- `adapt_profiles_to_hardware()` — 순수 함수, 입력을 바꾸지 않음.
  - Coral 있음: 주 카메라 `edgetpu`, 보조 카메라 활성화 + `tflite` 고정 (듀얼 카메라 모드).
    `backend`가 `auto`면 주=`picamera2`(CSI), 보조=`opencv`(USB)로 고정 (둘 다 CSI를 선점하려는 충돌 방지).
    보조 장치(`/dev/videoN`)가 없으면 단일 모드 유지.
  - Coral 없음: 보조 카메라 비활성화, 명시적 `edgetpu`는 `auto`로 내려 tflite 폴백.
- `--auto-hardware` 플래그로만 동작 (항상 켜면 대시보드에서 바꾼 `enabled`가 조용히 덮어써짐).
  시작 시와 `camera_config.json` 재로딩 시 적용.

### 3. 스트림 지연 개선 (`device/camera_live_pi.py`, `dashboard/backend/app/services/stream_fanout.py`)
- 원인: MJPEG 핸들러가 33ms마다 최신 JPEG을 **무조건 다시 전송** → 10fps 카메라가 30fps(같은 프레임 3번)로 나감.
- Pi: 새 프레임이 있을 때만 전송(`threading.Condition` + 시퀀스 번호), 송신 버퍼 64KB 제한, `TCP_NODELAY`.
- 대시보드 백엔드: 브라우저별 큐 3 → 1 (느린 뷰어에게는 최신 1장만).

### 4. 대시보드 프런트엔드
- **카메라 뷰:** Pi 스트림은 640×480(4:3)인데 16:9 카드에 `object-cover`라 위아래가 잘림 →
  4:3 + `object-contain`, 이름 표시줄을 영상 밖 헤더로 분리, 전체화면에서 영상이 꽉 차도록 CSS 추가.
- **카드 레이아웃:** 카메라 2대 이상인 장비는 그리드 2칸을 차지하고 1×2로 나란히 표시.
  썸네일 폭을 1대짜리와 같게 하려고 안쪽 간격을 60px(= 칸 간격 20 + 패딩 20×2)로 고정. 모든 카드에 카메라 이름 줄을 둬서 높이를 맞춤.
- **목록 API:** 비활성 카메라(`is_active=0`)를 장비 목록에서 제외 (103번 `cam1`이 "재연결 중" 칸으로 보이던 문제).
- **CPU 온도 색:** `utils/temperature.ts` 하나로 통일 — 60°C 미만 초록 / 60~80°C 주황(주의) / 80°C 이상 빨강(스로틀링).
- **리모컨 감도:** 장치 상세 → RF 탭에 임계값 슬라이더 + 숫자 입력 + 저장 버튼.

### 5. RF 리모컨 임계값 (`rssi_threshold`)
- 세 장치 모두 110 → **80** (2.5m 실측 신호 79~91, 잡음 최대 20~30대).
- Pi API `PUT /api/rf/detection` (1~255, 범위 밖 422), 대시보드 `PUT /api/devices/{id}/rf/detection`.
- 103번 RF를 켬 (`enabled: true`).
- 103번 SPI 활성화 (`/boot/firmware/config.txt`에 `dtparam=spi=on`, 60 · 89번은 이미 있었음).

### 6. 군집 제어
- **`group_window_ms` 80 → 600** (세 장치).
- **`group_follow_peers` 신설 (기본 `false`)** — 신호를 직접 감지한 장치끼리만 군집을 이루고,
  감지하지 못한 장치(예: 100m 떨어진 장치)는 동료의 `heard`를 받아도 재생하지 않음.
  이전 동작(감지 못해도 따라 재생)은 `true`로 복원 가능. 이전 커밋 `4c80fce5`의 동작을 기본값에서 뒤집은 것.
- 시작 로그에 `window=…ms follow_peers=…` 표시.

### 7. 하트비트로 장치 IP 자동 갱신 (`dashboard/backend/app/services/device_address.py`)
- 배경: 서버는 DB의 `Device.ip`로 Pi를 호출하는데 하트비트는 IP를 갱신하지 않아서, 새 Wi-Fi/DHCP로 Pi의 IP가 바뀌면
  Pi→서버 하트비트는 계속 오는데도 서버→Pi 호출(스트림, 카메라·RF 설정, 재부팅)이 전부 끊겼음.
- `PATCH /api/devices/me/heartbeat`가 TCP 출발지 주소가 등록된 IP와 다르면 `Device.ip`를 갱신 (달라졌을 때만 DB 쓰기).
- 서버가 이 IP로 제어 키(`X-Device-Key`)를 보내므로 안전장치를 둠:
  - 10/8 · 172.16/12 · 192.168/16 · 169.254/16 IPv4만 허용 (루프백, 공인 주소, IPv6 무시). `X-Forwarded-For`는 신뢰하지 않음.
  - 다른 기기가 이미 쓰는 IP면 바꾸지 않고 경고 로그만 남김.
- 허용 대역을 `ipaddress.is_private`로 판정하려 했으나 테스트가 문서용(203.0.113.0/24) · 벤치마크(198.18/15) · 예약(240/4)
  대역까지 통과시키는 것을 잡아내서 명시적 대역 목록으로 바꿈.
- 한계: Pi → 서버 방향이 살아 있어야 함. 새 PC로 옮기면 Pi의 `server_url`을 새 PC로 다시 심어야 함(재등록).
  이미 열려 있는 스트림 프록시 채널은 옛 URL을 붙들고 있다가 시청자가 나가면 정리됨.

## 트러블슈팅 (오늘 발생한 이슈)

### 103번 카메라 서비스 재시작 반복 — GPIO27 충돌
- `lgpio.error: 'GPIO busy'`. `visionguide-controls`(`gpio_controls.py`)가 GPIO27을 상태 LED로 이미 점유한 상태에서
  103번 유닛에만 있던 `--status-led 27`이 같은 핀을 잡으려 함.
- **해결:** 통일된 유닛으로 교체해 `--status-led` 제거.

### 89번 듀얼 카메라 — CSI 선점 충돌, 색상 반전
- 두 카메라가 `backend: auto`라 둘 다 picamera2로 CSI를 잡으려 하고, 진 쪽이 `/dev/video0`(raw unicam)으로 폴백해 영영 못 엶.
- **해결:** 듀얼 모드에서 주=`picamera2`, 보조=`opencv`로 고정.
- 보조 카메라를 `opencv`로 바꾸자 설정에 남아 있던 `swap_rb: true`(예전 picamera2 경로용 보정)가 색을 두 번 뒤집어 얼굴이 파랗게 나옴.
  **해결:** `swap_rb: false`. 적응형 로직 도입으로 생긴 회귀였고 프레임을 직접 받아 보고 발견함.

### 군집 제어가 가끔 겹쳐서 재생됨 — Wi-Fi 브로드캐스트 지연
- 군집 창(80ms) 안에 서로의 `heard`가 도착해야 하는데 UDP **브로드캐스트**가 늦게 도착.
- 로그(2대 이상이 들은 누름 21번): **14번(67%)이 "각자 나 혼자(1/1)"로 판단 → 동시 재생.**
  그중 12번은 감지 시차가 10ms 미만이라 감지 시차가 아니라 메시지 지연이 원인.
- 같은 AP에서 브로드캐스트 전달률 97~100%, **지연 중앙값 약 270~283ms, 최대 약 417~438ms**
  (유니캐스트: 중앙값 0.4~8ms). AP가 DTIM 주기로 모아서 내보내는 것과 일치하나, AP 설정은 확인하지 못했음.
- **해결(방안 A):** `group_window_ms` 600. 대가는 첫 안내 방송이 약 0.6초 늦어지는 것.

### 그 밖의 환경 이슈
- Windows `python`은 Microsoft Store 스텁이라 아무것도 실행하지 않음 → conda 환경의 `python.exe` 전체 경로 사용.
  Git Bash의 `/tmp`와 Windows python의 경로가 달라서 `C:\Users\...\AppData\Local\Temp`를 직접 지정.
- Claude Code 자동 모드 분류기가 원격 쓰기(배포, `config.txt` 수정)를 몇 번 거부함 →
  `/permissions`에서 해당 명령을 승인하고 재시도. `.claude/settings.local.json`에 `ssh`/`scp` 허용 규칙(`ailab@192.168.0.*`) 추가.

## 남은 과제 · 주의

- **군집 제어 근본 해결:** 브로드캐스트를 유니캐스트로 교체하면 창을 짧게 유지할 수 있음 (현재는 600ms 대기).
  AP의 DTIM 설정도 확인 필요. 창을 600ms로 키운 뒤에도 겹침이 남는지 실기 재측정 필요.
- **`group_follow_peers=false`의 부작용:** 신호가 약해 감지에 실패한 장치(예: 103번)는 조용히 있게 됨.
  "근처"는 감지 여부로만 판단하므로 서로 다른 장소에서 거의 동시에 두 리모컨을 누르면 한 라운드로 묶일 수 있음.
- **103번 RF:** 2.5m 신호가 약함(79~91). 임계값 80은 여유가 크지 않음. 안테나 연결 · 위치 점검, 거리별 반응률 측정 필요.
  60 · 89번은 임계값이 낮아져 오반응 위험이 조금 커짐 → 며칠간 로그에서 누르지 않은 시간대의 트리거 모니터링.
- **Pi API 무인증:** 포트 5000의 라우트는 재부팅/재시작을 제외하고 `X-Device-Key` 없이 같은 망에서 호출 가능
  (`/api/rf/detection`, `/api/rf/group`, `/api/rf/audio` 포함). 군집 UDP(47600)도 인증이 없음.
- **보안:** Pi `sudo` 비밀번호가 작업 중 대화에 노출되었고, 저장소 밖 로컬 스크립트(`ssh_probe.py`, 미커밋)에도 평문으로 남아 있음. 전시 후 변경 권장.
- **패키지 버전 차이:** 60번(opencv 5.0, fastapi 0.141 등)과 89 · 103번(opencv 4.x, fastapi 0.138 등). 지금은 문제가 없어 통일하지 않음.
- **정리 대상(미커밋):** `deploy/visionguide-device-89.service`, `visionguide-device-103.service`는 낡은 장치별 유닛 — 다시 배포하면 문제가 재발함.
- `visionguide-coral-reset.service`, `dashboard/backend/unlock_admin.py`, `ssh_probe.py` 등 작업과 무관한 미추적 파일은 이번 커밋에 포함하지 않음.
